# 客户特殊规则结构化与 Agent 规则表形成流程

日期：2026-07-07  
最近更新：2026-07-08  
适用范围：营销转码 Agent 的客户特殊规则结构化、业务确认、Agent 专用规则源形成。  
原则：本文只描述规则形成流程和维护口径，不代表已修改项目代码。

## 1. 背景

业务提供的新格式客户特殊需求原表用于提升营销转码 Agent 的客户特殊规则命中率。

当前目标不是直接替换项目原有 `transcode_rules.xlsx` 的 `特殊需求` Sheet，而是形成一套 Agent 专用规则源：

```text
业务原表
  -> 结构化草稿
  -> 业务确认
  -> Agent 可执行客户特殊规则表
  -> 营销转码 Agent 读取
```

这样可以避免影响普通转码、旧规则解析和其他功能。

## 4. 结构化草稿形成口径

草稿表保持原表有效客户行数，不把一个客户拆成多行。

当前草稿新增列：

```text
通用特殊规则_结构化
CCL特殊规则_结构化
非影响转码备注_结构化
待确认点
不纳入本次转码说明
结构化处理状态
本轮复核分类
本轮复核说明
本轮复核依据
本轮复核时间
```

当前草稿另有辅助说明 Sheet：

```text
待确认降噪说明
业务反馈处理说明
```

结构化状态：

```text
已结构化草稿
技术待支持
有待确认
仅参考信息
无可结构化内容
```

当前统计口径：

- `有待确认`：`待确认点` 不为空。
- `已结构化草稿`：结构化列中存在 `可执行草稿`，且无待确认点。
- `技术待支持`：业务规则和触发条件已明确，但当前 Agent 执行规则还缺尺寸覆盖、单边尺寸映射、物料编码条件、后缀位映射等技术能力；此类不再作为业务待确认问题。
- `仅参考信息`：结构化列或非影响备注中只有参考信息。
- `无可结构化内容`：没有可执行、没有参考、没有待确认。

## 5. 规则结构化字段建议

面向 Agent 可执行规则时，建议使用统一字段名。

常用覆盖字段：

```text
glue_code              胶系代码
thickness_rule         厚度/厚度换算规则
thickness_code         厚度代码
copper_code            铜箔规格代码
size_code              尺寸代码
glue_category_code     胶水类别代码
copper_type_code       铜箔类型/印字代码
grade_code             基板级别代码
tc_code                总厚/芯厚代码
struct_code            结构码
reference_note         参考备注
```

注意：`struct_code` 虽然是未来可执行字段，但 2026-07-08 业务口径已确认“组合结构本轮不考虑”，因此当前从草稿到 Agent 执行规则时暂不纳入。

当前不参与营销转码品名编码、只保留参考的字段：

```text
铜箔厂商
玻布厂商
配方代码
组合结构
排版结构/布号映射
PP规则
PP小片规则
订单语义规则
```

## 6. 参考逻辑和关联表

结构化草稿不能只看原表文本，需要结合项目已有规则逻辑。

### 6.1 胶系代码

参考：

```text
transcode_rules.xlsx / 胶系代码
transcode_engine.py / get_glue_code
```

用途：

- 判断客户特殊规则中的胶系是否已有标准映射。
- 判断是否需要用客户特殊规则覆盖胶系代码。

示例：

```text
NY2150=AS
NY3170HF=3C
```

可结构化为：

```text
条件胶系=NY2150 -> glue_code=AS
条件胶系=NY3170HF -> glue_code=3C
```

### 6.2 客户下单与胶系基板转换

参考：

```text
transcode_rules.xlsx / 客户下单与胶系基板转换
transcode_engine.py / apply_customer_order_rule
```

用途：

- 复核客户特殊规则中的胶系代码、基板级别、结构代码是否已有项目规则支撑。

已确认可参考的例子：

```text
珠海景旺：NY2150 -> AS
江西景旺：NY2150 -> 2S
景旺系：NY3150HCP -> RV
方正F7：NY2150 -> 2B/2C，结构 Y/Z
吉安满坤：NY2140 -> F1
江福昌发：NY2140 -> F1，NY1600 -> A2
```

注意：

```text
NY3150HC=RV/3H
```

如果没有选择条件，仍不能唯一确定 `RV` 还是 `3H`。但可以明确：

```text
RV -> 基板级别 A1
3H -> 基板级别 AL
```

### 6.3 编码规则

参考：

```text
transcode_rules.xlsx / 编码规则
transcode_engine.py / get_grade_code
transcode_engine.py / get_struct_code
```

用途：

- 复核基板级别代码。
- 复核结构码含义。

已确认口径：

- `TFT` -> `AT`
- 汽车板/车用/汽车专用 -> 汽车相关等级，通常为 `AC`
- `NY2140` 且厚度满足规则、铜厚不超过 1oz -> 可下 `F1`
- 湖北健鼎/超颖电子当前系统既有口径默认结构码 `E`，已确认可作为本次结构化草稿的可执行规则。

结构码注意：

```text
Y/Z
RV/3H
其他客户出现 E/H/I 且没有选择条件
```

这类多值如果缺少选择条件，不能强行唯一化。湖北健鼎/超颖电子例外：当前按系统既有逻辑默认 `E`，本次不新增 `H/I` 分支。

### 6.4 总芯厚转换

参考：

```text
transcode_rules.xlsx / 总芯厚转换
transcode_engine.py / calc_order_thickness
```

用途：

- 当特殊规则写明总厚/芯厚，或需要总芯厚转换时，按铜厚组合换算。

典型口径：

```text
全部芯厚 -> tc_code=C
全部总厚 -> tc_code=T
默认总厚，备注芯厚除外 -> 默认 T，命中芯厚备注时 C
默认芯厚，达到明确阈值需要转换 -> 按总芯厚转换表执行
默认总厚，低于明确阈值需要转换 -> 按总芯厚转换表执行
```

如果特殊规则已经写明触发条件，例如：

```text
基板厚度 < 0.8 需要进行芯总厚转换
基板厚度 >= 0.8 需要进行芯总厚转换
默认全部芯厚，基板厚度 >= 0.8 需要进行芯总厚转换
含铜是总厚且 < 0.8 时需要总厚转芯厚
```

则不应作为业务待确认，应结构化为：

```text
字段=基板厚度/总芯厚
覆盖字段=thickness_rule 或 tc_code
覆盖值=按总芯厚转换表执行
条件=原文明确阈值
状态=可执行草稿
依据=transcode_rules.xlsx/总芯厚转换 + transcode_engine.py/calc_order_thickness
```

只有特殊规则仅写“需要芯总厚转换”，但没有说明何时触发、以总厚还是芯厚为默认口径时，才保留待业务确认。

### 6.5 特殊需求旧 Sheet

参考：

```text
transcode_rules.xlsx / 特殊需求
transcode_engine.py / special_by_name、special_by_code
```

用途：

- 复核旧规则中已经存在的客户特殊口径。
- 作为新格式原表结构化的辅助依据。

使用原则：

- 新格式业务原表优先。
- 旧 `特殊需求` Sheet 只能作为辅助依据。
- 如果新旧规则冲突，必须标记待业务确认。

典型已辅助明确的规则：

```text
常熟敬鹏：0.71含以下芯厚，0.71以上总厚，FML为芯厚
奥士康/广东喜珍/森德科技：NY2140L无偏正公差 -> A，有偏正公差 -> S
深南系：排版结构 A=106 等属于参考信息，不纳入当前品名编码
```

### 6.6 尺寸规则

参考：

```text
transcode_engine.py / extract_size
transcode_engine.py / size_to_code
transcode_engine.py / get_special_size
```

通用尺寸编码规则：

```text
尺寸代码 = 宽度4位 + 长度4位
每边：整数2位 + 小数2位
```

例如：

```text
49*74 -> 49007400
74*49 -> 74004900
```

客户特殊尺寸规则：

```text
如果特殊需求明确写出 28*48=28504900，则按特殊需求原值执行。
```

注意：

- 系统旧 `get_special_size` 只识别“尺寸后跟 8 位码”的模式。
- 7 位码如果是业务明确写出的客户特殊映射，可以在草稿中保留原值。
- 如果规则已明确给出客户下单尺寸到厂内尺寸的映射，例如 `37*49=37.3*49.3`、`725.4*1244.6=28.56*49`，不应作为业务待确认；应标记为 `技术待支持`，后续由 Agent 支持尺寸覆盖。
- 如果只写单边尺寸映射，例如 `1888=74.3`、`2091=82.3`，也不应强行要求业务补 8 位尺寸码；应标记为 `技术待支持`，后续实现“单边替换后再组合生成尺寸码”。
- 如果引用外部表但项目内缺该表，例如“参考新美亚客户尺寸转换表”，仍需补充外部规则源，保留待业务确认或待资料补充。

### 6.7 铜箔规格和铜箔类型

参考：

```text
transcode_engine.py / extract_copper_spec
transcode_engine.py / copper_to_code
transcode_engine.py / get_copper_type_code
```

铜箔规格示例：

```text
H/H -> HH
J/J -> JJ
F/F -> FF
1/1 -> 11
R/R 如果业务写 R/R=F/F，则按客户特殊规则覆盖为 FF
```

铜箔类型示例：

```text
RTF  -> 特殊铜箔代码
RTF2 -> 特殊铜箔代码
HVLP/HVLP1 -> 特殊铜箔代码
HTE -> 常规铜，不作为特殊铜箔代码
有水印/无水印 -> 按印字/水印规则处理
```

已确认口径：

```text
订单未备注铜箔，默认 HTE -> 可按常规铜默认 W 处理
R/R=F/F 或 R/R=1.5/1.5 -> copper_code=FF
H/H=J/J -> copper_code=JJ
1/1=F/F -> copper_code=FF
1-/1-=K/K -> copper_code=KK
```

这类规则不应因为解析拆分异常而保留为业务待确认。

草稿表不是 Agent 最终执行表。它是业务确认稿。

```text

enabled

source_type
customer_code
sales_name

order_user

target_value
condition_glue
condition_thickness
condition_copper
condition_size
condition_keyword
condition_text
rule_explanation
confirmed_by

```

优先级建议：

```text
通用特殊规则 priority=10
CCL特殊规则 priority=20
参考信息 priority=90，不执行
```

执行范围：

```text
通用特殊规则 -> 全部物料
CCL特殊规则 -> CCL

```

真正规则表只接收：

```text

```

不得接收：

```text

涉及订单语义但尚未进入订单语义模块的规则

```

## 9. 待确认分类

仍需业务确认的典型情况：

```text
同一字段多值但没有选择条件：RV/3H、Y/Z、其他客户的 E/H/I
外部转换表缺失：例如新美亚尺寸转换表
新旧规则冲突：例如旧规则与新表对铜箔覆盖不一致
编码规则表缺少目标代码：例如 AB 等级
同一条件上下边界冲突：例如 0.9mm 同时含以上/含以下
规则内部优先级冲突：例如同一客户同时写非汽车板和基板下汽车板
条件过于口语化且无法落到字段
```

2026-07-08 业务反馈后，上述分类需再结合本轮执行范围判断：

- `组合结构` 不再作为当前业务待确认，即使出现 `Y/Z`、`E/H/I`、`L/M/Q`、`CP/CN`，本轮也不要求业务确认，直接移入“不纳入本次转码说明”。
- `铜箔厂商`、`玻布厂商`、`配方代码` 不作为当前业务待确认。
- 涉及订单备注或订单字段语义的规则，不作为当前转码规则待确认，标记为后续订单语义处理。
- 如果业务反馈已经给出明确选择，例如景旺系 `NY3150HC=RV/3H` 选择 `RV`，则从待确认移入可执行草稿。

可以明确但要拆分的情况：

```text
NY-A1或NY-A2=AC
NY2150或NY2170=AC
订单有双面字样 -> RTF，否则 HTE
有偏正公差 -> S，无偏正公差 -> A
默认 HTE -> 常规铜 W
明确阈值下总芯厚转换 -> 按总芯厚转换表执行
NY2140 且厚度/铜厚满足条件 -> F1
```

业务明确但技术待支持的情况：

```text
完整尺寸映射：37*49=37.3*49.3、725.4*1244.6=28.56*49
单边尺寸映射：1888=74.3、2091=82.3
尺寸统一放大：全部默认下加大0.3尺寸
物料编码条件：631=芯厚、632=总厚，需要稳定读取物料编码字段
编码后缀位映射：J0J0F0需要对应到*后24-30位数
客户专用厚度映射：003=3mil=0.079
客户订单备注字段作为铜箔规格来源
```

可以明确排除的情况：

```text
铜箔厂商
玻布厂商
配方代码
排版结构/布号映射
非影响转码备注
PP/PP小片规则
```

## 11. 后续维护步骤

后续如业务确认了待确认项，按以下步骤更新：

1. 在草稿表中定位客户行。
2. 修改对应结构化列。
3. 从 `待确认点` 中移除已确认内容。
4. 如果变为可执行规则，标记为 `状态=可执行草稿`。
5. 如果确认不参与转码，移动到 `不纳入本次转码说明` 或 `参考信息`。
6. 更新 `结构化处理状态`。
7. 更新统计说明。
8. 将本 MD 的“当前草稿状态”与“已确认口径”同步更新。
9. 只有业务确认后的可执行规则，才能进入 Agent 真正客户特殊规则表。

如果业务规则已经清楚但当前 Agent 尚不支持，应标记为 `技术待支持`，不要继续混在 `有待确认` 中。技术实现完成并回归通过后，再把对应行转为 `已结构化草稿` 或生成 Agent 真正规则表。

如果业务反馈确认某字段本轮不转，例如组合结构、铜箔厂商、玻布厂商、配方代码，应从 `待确认点` 移除，写入 `不纳入本次转码说明` 或复核说明，不再要求业务确认。

## 12. 代码开发约束

后续开发 Agent 规则读取逻辑时必须遵守：

- 不直接替换 `transcode_rules.xlsx` 的旧 `特殊需求` Sheet。
- 不影响普通转码功能。
- 只让营销转码 Agent 读取 Agent 专用规则源。
- 如果复用 `transcode_engine.py` 的共用能力，必须标明影响范围。
- 不继续使用个人桌面硬编码路径。
- 每次只开发一个功能点。
- 每次修改后必须回归测试。

建议正式落地顺序：

```text
1. 业务确认草稿
2. 生成 Agent 可执行规则表
3. 实现 Agent 专用规则加载器
4. 接入营销转码 Agent
5. 建立回归测试样本
6. 小范围验证
7. 再进入下一批规则优化
```
