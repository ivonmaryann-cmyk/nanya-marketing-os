# 营销转码 Agent 优化上线方案

## 文档信息

- 日期：2026-07-07
- 版本定位：营销转码 Agent 优化评估版 v2
- 当前原则：本阶段只做评估和方案确认，未修改代码
- 开发范围：仅限营销转码 Agent 功能
- 明确不纳入范围：PP / R/C / RC / 半固化片 / 含树脂百分比 `%` 的规格转码

## 背景

当前项目是接手项目，历史开发主要通过 Codex 辅助完成。项目已具备基础的营销转码能力，业务反馈营销转码 Agent 已完成基础功能，但在业务校验文件中仍存在较多错误样例。

本次基于业务提供的 `Agent转码处理结果.xlsx` 做评估。分析只参考第一个 Sheet 和第四个 Sheet：

- 第一个 Sheet：业务正确/错误判断、目标品名、Agent 输出结果、错误说明。
- 第四个 Sheet：Agent 规则命中汇总。

第二、第三个 Sheet 不作为本次分析依据。

2026-07-07 补充确认：

- 当前最高优先级调整为“新格式客户特殊需求表接入营销转码 Agent”。
- 新格式表不替换 `transcode_rules.xlsx` 的 `特殊需求` Sheet。
- 新格式表作为营销转码 Agent 专用规则源。
- 只解析 `CCL特殊规则` 和 `通用特殊规则`。
- `通用特殊规则` 优先级高于 `CCL特殊规则`。
- `非影响转码备注` 暂时只作为参考，不直接生成可执行规则。
- `PP特殊规则` 和 `PP小片特殊规则` 暂不解析、不执行、不优化。

## 上线目标

本次优化目标不是重构整个系统，而是在低风险前提下提升营销转码 Agent 对 CCL 类规格的准确率。

核心目标：

- 安全接入新格式客户特殊需求表。
- 将客户特殊规则转换成 Agent 可执行的内部统一规则。
- 修复高频明确 bug。
- 降低高置信错码。
- 保持其他功能不受影响。
- 不修改 PP / RC / 半固化片转码范围。
- 不改动方正、深南、沪士、博敏、在途核对、账号、历史记录、规则管理等非目标模块。

## 必须遵守的开发边界

本项目已有协作开发说明要求：

- `storage/` 不进入 Git。
- 不提交日志、缓存、临时包、备份文件和本地运行产物。
- 修改前要保留当前基线。
- 关键功能变更后必须本地验证。
- 服务器部署时只替换代码文件，保留生产 `storage/`。

本次营销转码 Agent 优化额外要求：

- 每次开发只能开发一个功能点。
- 一个功能点开发完成后，必须完成回归测试，才能进入下一个功能点。
- 不能为了修 Agent 误改普通转码、报价、在途核对等功能。
- 优先修改 Agent 层逻辑，不优先修改底层共用转码引擎。
- 如确实需要修改共用函数，必须标明影响范围，并增加开关、参数或适配层，避免影响其他调用方。
- 不允许一次性重构 `transcode_engine.py`。
- 不允许将业务猜测写成全局规则。
- 不允许直接替换 `transcode_rules.xlsx` 的 `特殊需求` Sheet。
- 不允许让新格式客户特殊需求表影响普通营销转码、在途核对或其他报价功能。
- 不允许解析或执行 `PP特殊规则`、`PP小片特殊规则`。

## P0：新格式客户特殊规则源接入

### 当前确认口径

新格式客户特殊需求表字段为：

```text
客户代码
业务员
客户简称
下单员
CCL特殊规则
PP特殊规则
PP小片特殊规则
通用特殊规则
非影响转码备注
```

本次只处理：

```text
CCL特殊规则
通用特殊规则
```

暂不处理：

```text
PP特殊规则
PP小片特殊规则
```

参考但不执行：

```text
非影响转码备注
```

### 设计结论

新格式客户特殊需求表不应直接替换 `transcode_rules.xlsx` 的 `特殊需求` Sheet。

业务给出的“客户特殊需求新格式”是原始业务表，不应作为 Agent 直接执行的规则表。它必须先经过 Codex/模型/人工辅助结构化，转换为内部统一格式后，Agent 才读取转换后的执行规则。

原因：

- `transcode_engine.py` 当前按旧格式固定列位置读取 `特殊需求`。
- 新格式列含义已变化，直接替换会导致旧逻辑读取错位。
- 普通营销转码、Agent 基础转码、在途核对品名判断可能间接受影响。
- 新格式表虽然已经人工清洗，但仍包含口语化、多规则混写、条件不完整、备注性描述等内容，直接执行风险较高。

正确设计：

```text
业务原始客户特殊需求表
        ↓
Codex / 模型 / 人工辅助结构化
        ↓
内部统一格式规则草稿
        ↓
人工确认 / 程序校验
        ↓
Agent 执行规则表
        ↓
营销转码 Agent 读取执行
```

禁止设计：

```text
业务原始客户特殊需求表
        ↓
替换 transcode_rules.xlsx 的特殊需求 Sheet
        ↓
普通转码 / Agent / 其他功能一起读取
```

同时也禁止：

```text
业务原始客户特殊需求表
        ↓
Agent 运行时直接读取并执行
```

原因是原始业务表不是稳定的机器执行格式，必须通过结构化转换和校验。

### 推荐存储方式

沿用现有 Agent 规则版本目录：

```text
storage/rules/transcode_agent/versions/<version>/
```

每次上传后保存：

```text
customer_special_master.xlsx
customer_special_structured_draft.xlsx
transcode_agent_rules.xlsx
```

其中：

- `customer_special_master.xlsx`：业务原始新格式客户特殊需求表。
- `customer_special_structured_draft.xlsx`：Codex/模型/人工辅助转换后的内部结构化规则草稿，未确认前不直接执行。
- `transcode_agent_rules.xlsx`：通过人工确认和程序校验后的 Agent 执行规则表，Agent 正式运行只读取该文件。

如果第一阶段暂不落地草稿文件，也必须在流程上区分：

```text
原始业务表 != Agent 执行表
```

Agent 只能读取转换后的执行规则，不能直接读取业务原表。

### 内部统一规则格式

转换后的内部结构化规则建议至少包含以下字段：

```text
规则ID
启用
待确认
客户代码
客户简称
来源字段
原始规则文本
原始来源行号
物料范围
优先级来源
目标字段
条件胶系
条件厚度
条件铜厚
条件尺寸
条件关键词
匹配来源字段
覆盖字段
覆盖值
是否强制执行
风险等级
规则解释
冲突说明
```

其中必须保留：

```text
原始规则文本
来源字段
原始来源行号
```

这样业务追问某条 Agent 规则来源时，可以从执行规则追溯到业务原表。

### Agent 读取原则

Agent 正式运行时只读取：

```text
transcode_agent_rules.xlsx
```

不直接读取：

```text
customer_special_master.xlsx
customer_special_structured_draft.xlsx
```

原因：

- 原始表是业务表达，不是机器执行规则。
- 草稿表可能包含待确认、冲突、不完整规则。
- 执行表才是通过校验、可审计、可回滚的稳定规则源。

### 解析规则

#### CCL特殊规则

必须解析为 Agent 可执行或待确认规则。

支持字段：

```text
胶系
基板厚度
铜箔规格
基板尺寸
胶水类别
铜箔类型+印字/非印字
基板级别
总/芯厚
组合结构
铜箔厂商
玻布厂商
配方代码
```

其中，只有会影响编码的字段可以进入正式转码覆盖：

```text
胶系
基板厚度
铜箔规格
基板尺寸
胶水类别
铜箔类型+印字/非印字
基板级别
总/芯厚
组合结构
```

铜箔厂商、玻布厂商、配方代码暂不直接影响当前品名编码时，应先作为扩展字段或待确认，不应贸然参与正式编码。

#### 通用特殊规则

通用特殊规则必须抓取，并且优先级高于 CCL特殊规则。

定义：

```text
通用特殊规则适用于该客户所有物料；
本阶段营销转码 Agent 只取其中 CCL 相关规则参与 CCL 转码。
```

执行优先级：

```text
通用特殊规则 > CCL特殊规则 > 基础转码规则
```

冲突处理：

```text
如果通用特殊规则和 CCL特殊规则覆盖同一字段且结果不同，不允许静默覆盖。
应进入待确认，或在规则导入阶段提示冲突。
```

示例：

```text
通用特殊规则：胶系：NY2150=AS
CCL特殊规则：胶系：NY2150=2B
```

该场景必须标记冲突，不能直接按优先级吞掉低优先级规则。

#### 非影响转码备注

处理方式：

```text
读取
保存
展示
作为模型/人工参考
不直接生成强制执行规则
不参与正式转码
```

如果从该列发现疑似影响编码内容，只能生成：

```text
候选规则
待确认规则
```

不能直接执行。

#### PP特殊规则 / PP小片特殊规则

本阶段处理方式：

```text
不解析
不执行
不进入 Agent 机器规则数统计
不参与转码
不参与本轮准确率评估
```

### 影响评估

| 项目 | 影响 |
|---|---|
| 普通营销转码 | 不应影响 |
| 营销转码 Agent | 主要影响对象 |
| 方正/深南/沪士/博敏 | 不应影响 |
| 在途核对 | 不应影响 |
| `transcode_rules.xlsx` | 不替换，不影响 |
| `storage/` | 只新增 Agent 规则版本，不改历史数据结构 |
| 风险 | 中 |

风险主要来自：

- 新格式表仍有口语化内容。
- 通用特殊规则优先级更高，若解析错误影响更大。
- 同一客户同一字段可能出现冲突。
- 自然语言规则可能缺少条件。

### 验收标准

- 上传新格式客户特殊需求表后，保留业务原始表。
- 原始业务表经过 Codex/模型/人工辅助转换后，生成内部结构化规则草稿。
- 草稿经过人工确认和程序校验后，生成 Agent 执行规则表。
- Agent 正式运行只读取转换后的执行规则表，不直接读取业务原表。
- 普通营销转码仍使用原 `transcode_rules.xlsx`。
- `PP特殊规则`、`PP小片特殊规则` 不出现在机器规则数中。
- `通用特殊规则` 可被解析，并优先于 `CCL特殊规则`。
- 冲突规则进入待确认。
- `非影响转码备注` 不直接执行。
- 使用昨天 Agent 错误样例回归后，客户特殊规则相关错误应下降。

## P1：模型辅助规则结构化

### 是否建议接入模型

建议接入，但模型只作为规则整理助手，不作为正式转码裁判。

模型适用场景：

```text
新格式客户特殊需求表仍有口语化内容
同一句话包含多个规则
规则缺少结构化条件
需要判断是否可执行
需要区分规则、备注、待确认项
```

模型不应做：

```text
直接输出最终编码
直接覆盖生产规则
直接参与每条正式转码出码
绕过人工确认
```

### 前期实施方式

前期可以先由 Codex/人工辅助将业务原表转成内部结构化规则草稿。这个阶段不要求马上接模型 API，先把内部格式、校验规则和业务确认流程跑通。

推荐流程：

```text
业务给新格式客户特殊需求原表
        ↓
保留原表 customer_special_master.xlsx
        ↓
Codex/人工提取结构化规则草稿 customer_special_structured_draft.xlsx
        ↓
业务确认
        ↓
程序校验
        ↓
生成 Agent 执行规则表 transcode_agent_rules.xlsx
        ↓
Agent 读取执行规则表
        ↓
回归测试
```

这样不需要一开始就接模型 API，风险更低。

前期 Codex/人工结构化的重点：

- 拆分一段话里的多条规则。
- 判断规则属于 `CCL特殊规则`、`通用特殊规则`、`非影响转码备注` 还是暂不处理的 PP 规则。
- 判断规则是否条件完整。
- 判断是否可直接执行。
- 判断是否需要人工确认。
- 保留原始文本、来源字段、来源行号。

如果规则存在歧义，例如：

```text
NY3150HC=RV或3H
```

应进入待确认，不允许直接生成强制执行规则。

### 后期模型 API 方案

后续可使用模型进行批量语义结构化。

推荐模型：

```text
默认：gpt-4.1-mini
复杂规则复核：gpt-4.1
```

模型输出必须是固定 JSON，不允许自由文本。

示例：

```json
{
  "customer_code": "105007",
  "customer_name": "湖奥士康",
  "source_column": "CCL特殊规则",
  "source_text": "铜箔规格：R/R=F/F",
  "material_scope": "CCL",
  "priority_source": "CCL",
  "target_field": "copper_code",
  "conditions": {
    "copper": "R/R"
  },
  "override_value": "FF",
  "executable": true,
  "need_confirm": false,
  "risk_level": "low",
  "explanation": "仅当客户规格铜厚明确为R/R时，将铜厚代码覆盖为FF"
}
```

模糊规则示例：

```text
胶系：NY3150HC=RV或3H
```

模型应输出：

```json
{
  "customer_code": "103890",
  "customer_name": "珠海景旺",
  "source_column": "CCL特殊规则",
  "source_text": "胶系：NY3150HC=RV或3H",
  "material_scope": "CCL",
  "target_field": "glue_code",
  "conditions": {
    "glue": "NY3150HC"
  },
  "override_value": "",
  "executable": false,
  "need_confirm": true,
  "risk_level": "high",
  "explanation": "同一条件存在RV或3H两个目标值，缺少区分条件"
}
```

### 程序校验要求

模型输出后必须经过程序校验：

- 字段是否合法。
- 覆盖值是否合法。
- 条件是否足够。
- 是否客户级绑定。
- 是否出现多值冲突。
- 是否误用了 PP 字段。
- 是否来自非影响转码备注。

只有通过校验且不需要确认的规则，才允许进入可执行规则。

## 原第一批单点修复调整为 P2

在新格式规则源接入完成前，原本第一批单点修复不作为最高优先级。

原因：

```text
昨天的大量错误根因是客户特殊规则没有稳定解析和执行。
如果规则入口不先修好，单点修复会继续散落，后续仍然不可维护。
```

调整后顺序：

```text
P0：新格式客户特殊规则源接入
P1：模型/人工辅助规则结构化
P2：R/R=FF、VLP1、置信度降权等单点修复
```

## P2：单点修复建议上线内容

P2 只建议做低风险、高收益项：

1. R/R=FF 过度覆盖修复。
2. VLP1=HVLP1 铜箔类型别名。
3. Agent 置信度默认值降权。

不建议 P2 阶段处理：

- 全局胶系映射重写。
- 全局厚度规则重写。
- 全局基板等级默认规则修改。
- PP/RC/% 转码。

原因：P2 目标是在 P0 规则入口稳定后，快速降低明确错码，同时不影响其他功能。

## 修改项一：R/R=FF 过度覆盖修复

### 当前问题

客户特殊规则中存在类似：

```text
R/R = FF
```

但 Agent 在部分样例中把该规则错误应用到了：

```text
H/H
2/2
1/2
```

导致铜厚被错误覆盖成 `FF`。

### 涉及文件

优先检查：

- `fangzheng_web_app/transcode_agent_rules.py`
- `fangzheng_web_app/transcode_agent_service.py`

### 是否涉及共用功能

原则上不应涉及共用功能。

不建议修改：

- `fangzheng_web_app/transcode_engine.py` 的通用铜厚解析。

### 推荐修复方式

只在 Agent 规则匹配层收窄条件：

- 当前规格铜厚必须明确等于 `R/R`，才能执行 `R/R -> FF`。
- 如果当前规格铜厚是 `H/H`、`2/2`、`1/2`，不得执行 `R/R -> FF`。
- 管道格式规格中，例如 `有卤基板|NY2150|0.710|2/2|...`，应优先使用规格中明确的铜厚 `2/2`。
- 如果特殊规则只有自然语言描述，没有明确条件铜厚，不应强制执行。

### 影响评估

| 项目 | 影响 |
|---|---|
| 普通转码 | 不应影响 |
| Agent 转码 | 只收窄错误覆盖 |
| 其他报价功能 | 不应影响 |
| 在途核对 | 不应影响 |
| 风险 | 低 |

### 回归要求

必须验证：

- 被误改为 `FF` 的样例恢复为原铜厚。
- 真正 `R/R` 的样例仍能转为 `FF`。
- 原本正确的 `H/H`、`1/1`、`2/2` 样例不变化。

## 修改项二：VLP1=HVLP1 铜箔类型别名

### 当前问题

业务认为：

```text
VLP1 = HVLP1 -> O
```

当前系统可能按 `VLP` 命中，输出 `L`。

### 涉及文件

优先检查：

- `fangzheng_web_app/transcode_engine.py`
- `fangzheng_web_app/transcode_agent_rules.py`

### 是否涉及共用功能

可能涉及共用铜箔类型识别。

如修改 `transcode_engine.py`，会影响普通转码功能，所以必须谨慎。

### 推荐修复方式

优先在 Agent 层补别名规则：

- `VLP1` 优先匹配为 `HVLP1`。
- 输出铜箔类型代码 `O`。

如必须修改共用引擎，则必须保证长词优先：

```text
VLP1 先于 VLP 匹配
```

### 影响评估

| 项目 | 影响 |
|---|---|
| 普通转码 | 如果改引擎会影响，若只改 Agent 则不影响 |
| Agent 转码 | 修复明确错误 |
| 其他功能 | 低风险 |
| 风险 | 低 |

### 回归要求

必须验证：

- `VLP1` 输出 `O`。
- `HVLP1` 仍输出 `O`。
- 普通 `VLP` 仍按原规则输出，不被误改。

## 修改项三：Agent 置信度默认值降权

### 当前问题

当前 Agent 的高置信更多表示字段被成功解析，不等于业务规则正确。

典型问题：

- 默认 `A1` 得分较高。
- 默认 `W` 得分较高。
- 没有命中特殊规则也可能高置信出码。
- 第四个 Sheet 显示待确认为 0，但业务错误仍很多。

### 涉及文件

优先检查：

- `fangzheng_web_app/transcode_agent_service.py`

### 是否涉及共用功能

不应涉及共用功能。

该项应只影响 Agent 的状态判断：

- 成功
- 待确认
- 失败
- 字段证据链置信度

不应影响基础转码结果。

### 推荐修复方式

调整 Agent 评分策略：

- 默认 `A1` 不直接视为高可靠。
- 默认 `W` 不直接视为高可靠。
- 客户存在特殊规则但未命中时，默认字段降分。
- 规则条件不足、模糊、冲突时进入待确认。
- 高置信必须代表规则来源可靠，而不仅是字段能解析。

### 影响评估

| 项目 | 影响 |
|---|---|
| 普通转码 | 不影响 |
| Agent 转码 | 可能减少高置信出码，增加待确认 |
| 业务准确性 | 提升 |
| 其他功能 | 不影响 |
| 风险 | 中低 |

### 回归要求

必须验证：

- 原本高置信但业务错误的默认 `A1` 样例进入待确认或被正确规则覆盖。
- 原本明确正确的样例仍能高置信出码。
- 待确认数量合理增加。

## 修改项六：厚度解析增强

### 当前问题

### 是否涉及共用功能

是。

- `28_C` 是否代表厚度。

必须限制：

- 绑定客户。
- 绑定特定格式。

| 其他报价功能 | 通常不影响，但需验证 |
| 风险 | 中 |

### 回归要求

必须增加厚度专项回归：

- mm 厚度。
- mil 厚度。
- inch 厚度。
- 含铜小于 0.8 转芯厚。
- 不含铜芯厚。
- 客户特殊厚度。

## 低耦合实现原则

后续开发必须遵守：

1. Agent 层优先。

   能在 `transcode_agent_service.py` 或 Agent 规则包解决的问题，不下沉到 `transcode_engine.py`。

2. 共用引擎谨慎修改。

   如果必须修改 `transcode_engine.py`，必须说明：

   - 被哪些功能调用。
   - 修改前后行为。
   - 是否需要参数开关。
   - 是否影响普通转码。

3. 规则优先于硬编码。

   客户差异应进入结构化规则，不应散落在 Python `if/else` 中。

4. 客户级规则必须绑定客户。

   不允许把客户特殊口径做成全局默认。

5. 默认值不能高置信。

   默认 `A1`、默认 `W`、默认尺寸、默认总芯厚，在特殊客户场景下应降低置信度或进入待确认。

6. 不确定则待确认。

   Agent 优化目标不是强行出码，而是减少高置信错误。

```text
只解析 CCL特殊规则 + 通用特殊规则
通用特殊规则优先级高于 CCL特殊规则
PP/PP小片不解析不执行
非影响转码备注只作为参考
```

原因是昨天大量错误的根因都指向客户特殊规则没有稳定、准确、可审计地转换成 Agent 可执行规则。先修规则入口，后续再做 R/R、VLP1、基板等级、厚度、胶系等单点修复，才符合低耦合和可回归的开发原则。
