# 任务与人效看板

## 2026-09 简化版（以下口径取代旧版统计说明）

- 我的任务仅追踪；团队含任务追踪和全员人效。移除手工工时登记入口及节省人力测算，旧工时数据保留但不参与新看板。
- 默认今天，查询会同时更新汇总、明细、人员统计；快捷日期和分页保留类型、负责人条件，重新查询回到第一页。
- 任务追踪按收信日期选取邮件，显示当前待处理、处理中、已完成；人效完成量按完成日期统计。人员下钻“查看完成订单”按完成日期列出，包含跨天任务，其上方数字也按该完成集合显示。
- 收信日期优先 received_at，缺失使用 sent_at，再缺失使用入库时间；内部无时区值按 UTC，邮件无时区值按北京时间。
- 首次发起订单提取时保存 processing_started 事件；重试不重置。只查看看板不开始计时。旧任务未记录开始事件的耗时不推算。
- 耗时是开始到业务完成的自然时间，含系统和人工等待，不是人工工时。平均值仅覆盖有完整时间的已完成任务，并展示计时覆盖单数。
- 完成项次取成功提交事件的 line_count，不取可变模板行数；缺失单独提示。现有修单代码只有 APS 提交时，不能视为已完成；后续 NYEOS 成功回写须保存完成时间和成功项次数，才能进入完成统计。
- 测试期保留模拟完成，明确标注。不能将这些数字用于正式减员结论。
- 邮箱 + Message-ID 去重，无 Message-ID 时使用邮箱 + 文件夹 + UID。多个案例选已完成优先、已开始其次、最早案例最后的唯一记录，按其负责人归属。这是统计去重，不改变业务任务归属或实现共享协作。
- 无精确标识的跨文件夹重复邮件仍可能重复；未路由邮件归属邮箱账号所有人。多次操作同一邮件按一个任务计，不代表实际 NYEOS 订单头数量。
- 本轮无需新增表。团队权限仍沿用管理员角色。

旧版说明留存如下，仅用于历史实现追溯。

## 入口及权限

侧栏「看板」包含「我的任务看板」与「团队任务看板」。我的看板仅查询当前登录员工的录单、修改订单案例；团队看板沿用现有管理员权限。管理员查看他人任务仅可追踪，不能通过此页面修改业务或代填工时。普通员工直接访问团队地址返回 403，访问他人的任务返回 404。

任务追踪提供日期、负责人、业务类型、任务范围筛选、人员负荷、每日流入/完成、当前阶段、分页明细与事件时间线。进入业务处理仍使用原有业务页面及权限，不会触发邮件同步或重新分流。

## 部署

新增表 `order_task_work_samples` 仅保存主动登记的实际人工分钟数、工作类型、业务日期、操作者、说明和创建时间。不会更新原订单、邮件和任务状态。UUID 提交标识避免同一表单重复提交被多次计入。

PostgreSQL 按现有迁移流程执行 `migrations/automation/postgresql/0012_task_board_work_samples.sql`，或在项目根目录运行幂等初始化命令（SQLite 同样适用）：

```sh
APP_STARTUP_MAINTENANCE_ENABLED=false .venv/bin/python -m flask --app fangzheng_web_app:create_app task_boards init-db
```

随后重启 Web 服务使新蓝图和菜单生效。未初始化工时表时，任务统计仍可读取，工时显示缺失提示而不自动建表。当前部署账号如无 DDL 权限，由数据库管理员执行迁移。

## 统计口径

- 按系统案例计数，不按邮件明细行计数；只包含录单与修改订单。
- 日期采用北京时间；内部无时区时间按现有 UTC 约定解析，邮件无时区时间按业务北京时间解析。
- 本期新增：案例创建日期在所选范围。本期业务完成：状态为 archived 且 workflow_stage 为 completed，并有范围内的 completed_at。
- 当前待办、业务完成待回复是跨日期的当前存量，不是历史时点快照。发送成功事件用于判断已回复；APS 接收成功不能视为业务完成。
- 任务年龄仅是创建以来的天数，不是超期或人工耗时。历史记录缺少完成时间时，不猜测其完成日期。
- 人员工时是本人主动登记的核对、操作与返工分钟数，不采集页面停留时间。按登记的工作日期统计；样本平均值是所选期间登记分钟总和 / 有登记的任务数，不是完整生命周期均耗时。
- 未登记为缺失而不是零。没有人工基准、任务时限、可用工时前，不计算节省工时、按时完成率或可减少人数。
- 模拟录单完成会显式提示；当前测试数据不可作为正式人效结论。

## 当前边界与后续

这是现有任务数据上的追踪视图，不是共享邮箱协作改造。同一邮箱重复接入多个员工可能产生重复案例；完成邮箱级唯一任务、负责人及协作事件设计前，不能将案例总数等同于部门唯一订单数。

当前团队可见范围使用既有管理员角色，尚无独立「营管领导」角色。后续应增加明确的团队范围授权，而非给领导开放全部系统管理员权限。

当前在服务层聚合案例历史，已在现有测试规模验证；大规模增长后需按日期/团队数据库聚合、分页查询与索引性能验证。工时登记暂不提供修改/删除，后续如需纠错应增加可审计的冲正记录。后续人效分析应先建立分业务类型/复杂度的代表性人工基准、质量和返工指标，再评估人员容量，避免仅按任务数量排名。
