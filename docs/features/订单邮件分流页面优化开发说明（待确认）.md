# 订单邮件分流页面优化开发说明（待确认）

- 状态：已完成开发，待页面验收
- 日期：2026-08-24
- 范围：订单邮件分流的列表页、历史补抓入口、邮件详情页，以及首次订单提取的异步化；不改变现有邮件抓取、分流和订单识别规则

## 1. 背景与目标

当前页面已经可以完成邮件抓取、业务分流和进入订单提取流程，但存在三个使用问题：

1. `补充近7天邮件` 与 `手动同步` 并列，用户难以理解二者是否重复，以及各自适用场景。
2. 列表的判断依据标签较多、信息重复，业务人员无法快速得知“这封邮件是谁的、要做什么、下一步点哪里”。
3. 邮件详情页把最重要的“业务分流与进度”收在右侧抽屉内，桌面端处理邮件时不够直观；正文区域对短邮件留白过多，附件信息也不足。

本次优化目标：

- 把“日常同步”和“历史补抓”组织成一个清晰入口。
- 让列表在一屏内回答：来源、客户、内容摘要、附件、当前状态、下一步动作。
- 让详情页优先展示业务判断与待办动作，同时保留原始邮件作为核对依据。
- 保持现有分流、识别、去重和接口提交逻辑不变；仅把耗时的首次 PDF/图片识别移出网页请求。

## 2. 当前功能与本次口径

| 操作 | 当前实现 | 本次页面口径 |
| --- | --- | --- |
| 手动同步 | 同步当前业务邮箱今天和昨天的邮件（`lookback_days=2`） | 改名为“同步新邮件”，作为日常主操作 |
| 补充近7天邮件 | 补抓近 7 天邮件，并由既有去重机制过滤重复邮件 | 作为“同步新邮件”下的历史补抓选项 |
| 历史补抓 30 天 | 后端已支持 1–30 天范围 | 本次在下拉选项中提供，标识为按需操作 |

说明：日常同步与历史补抓复用同一抓取流程，区别仅是扫描时间范围。补抓不是重复建单：已入库邮件仍由既有唯一标识去重。

## 3. 页面方案

### 3.1 邮件列表页

列表每封邮件按“识别结果 + 业务动作”呈现，而不是堆叠所有规则命中标签。

每行信息：

| 区域 | 展示内容 | 规则 |
| --- | --- | --- |
| 主标题 | 邮件主题 | 保留完整主题；超长时截断并可在详情查看 |
| 来源 | 发件人名称、邮箱、收件时间 | 统一为 `名称 · email · 时间`，不重复显示相同邮箱 |
| 客户识别 | `已匹配客户：客户简称` / `客户待确认` | 仅唯一匹配时展示具体客户；无法唯一匹配时不猜测 |
| 内容摘要 | 清洗后的正文或附件识别摘要 | 一行展示，优先保留订单号、交期、报价等业务信息 |
| 附件 | 文件名、文件类型、附件数量 | 例如 `MZPOM...pdf · PDF · 1 个附件` |
| 业务类别 | 录单、修改订单、报价、待分流等 | 使用现有分流结果，不调整规则优先级 |
| 下一步 | 面向操作的状态与按钮 | 例如“下一步：提取订单信息 / 去处理”，替换笼统的“查看详情” |

规则证据不再在列表逐项平铺。列表最多显示两个高价值标签（如“唯一客户匹配”“订单号已识别”）；完整命中依据留在详情页中查看。

列表页顶部新增或调整：

- 显示当前业务邮箱、最近一次成功同步时间、同步新增数量与同步状态。
- 保留现有日期导航和业务类型筛选。
- 右侧“工作闭环”统计维持原有统计口径；本期不改变任务状态计算。后续可再把统计项做成可点击筛选入口。

### 3.2 同步与历史补抓入口

页面只保留一个主按钮：`同步新邮件 ▾`。

下拉菜单：

| 选项 | 执行范围 | 使用场景 |
| --- | --- | --- |
| 同步今天与昨天的邮件 | 2 天 | 每日正常操作，作为默认项 |
| 补抓近 7 天邮件 | 7 天 | 短期遗漏、网络异常恢复后补齐 |
| 补抓近 30 天邮件 | 30 天 | 首次接入或较长时间未抓取时按需使用 |

交互要求：

- 用户点击任何同步选项后，应显示“同步中 / 已完成 / 失败”的明确状态；完成后显示新增邮件数和完成时间。
- 所有入口必须针对当前查看的业务邮箱执行。
- 若用户配置多个业务邮箱，页面必须先明确当前邮箱或提供邮箱选择，不允许日常同步和历史补抓落到不同账号。
- 历史补抓需保留“系统会自动去重”的提示，避免用户担心重复建单。

### 3.3 邮件详情页

详情页调整为“先决策、后核对”的两栏结构。

#### 顶部决策卡

在邮件标题下固定展示三项：

| 信息 | 示例 |
| --- | --- |
| 客户识别 | 上海博敏电子；唯一匹配；置信度高 |
| 系统分流建议 | 录单；依据为主题、PDF 附件、订单号 |
| 下一步 | 提取订单信息；当前为待接口提交 |

#### 左侧：原始邮件核对

- 发件人、邮件时间、附件数量。
- 附件显示：文件名、文件类型、文件大小、解析或识别状态；提供预览和下载。
- 正文默认展示清洗后的可读文本，高度随内容自适应；“查看原始 HTML 正文”按需展开。
- 邮件正文中的外部链接仅展示，不自动访问。

#### 右侧：业务分流与进度

- 桌面端默认展开，不再收起为竖向侧边标签。
- 展示分流至录单后的关键节点与当前状态。
- 主按钮保持为“提取邮件订单信息到内销模板”。首次点击只创建后台任务并立即返回详情页，页面展示“排队中／提取中／完成／失败”；完成后自动刷新为打开内销模板。
- 对需要人工介入的邮件，显示“修改业务分类”；人工修改后应保留操作人、时间、修改前后分类和原因。若现有操作日志无法承载这些字段，此项另行补充数据结构迁移。

## 4. 不在本次范围内

- 不调整订单、修改订单、报价等业务分流规则本身。
- 不改变邮件抓取协议、IMAP 配置、去重逻辑或附件落盘位置。
- 不自动打开或访问邮件正文中的外部供应商链接。
- 不在本期新增跨邮箱聚合的统一工作台；多邮箱时先保证操作对象明确一致。
- 不改变接口提交和内销模板生成结果、识别规则或原始附件内容。

## 5. 涉及文件与技术实现方向

预计涉及：

| 文件 | 预期改动 |
| --- | --- |
| `templates/order_automation.html` | 列表信息层级、同步下拉入口、同步状态展示 |
| `templates/order_automation_case.html` | 顶部决策卡、附件信息、正文展示、默认展开的处理面板 |
| `fangzheng_web_app/mail_transcode_agent/routes.py` 或现有订单邮件路由 | 统一日常同步和历史补抓入口的参数与响应文案 |
| `fangzheng_web_app/mail_transcode_agent/mail_fetch_service.py` | 复用现有 2 / 7 / 30 天抓取能力；如有必要补充同步结果返回信息 |
| `fangzheng_web_app/order_entry_service.py` | 为首次订单提取增加持久化后台任务、状态查询和失败重试入口 |
| `fangzheng_web_app/order_entry_template_worker.py` | 新增独立后台进程，执行耗时的 PDF/图片解析 |
| `migrations/automation/postgresql/0005_order_entry_template_tasks.sql` | 新增 PostgreSQL 提取任务状态表 |

实现原则：优先复用现有识别接口；新增的仅是订单提取任务状态，不改变既有邮件、分流和模板数据。

- [ ] 页面只展示一个日常主入口“同步新邮件”。
- [ ] 用户可从同一入口选择 2 天、7 天、30 天范围。
- [ ] 日常同步与历史补抓都明确作用于当前业务邮箱。
- [ ] 成功、处理中、失败均有可见反馈；历史补抓提示会自动去重。

### 详情页

- [ ] 进入详情即可看到客户识别、分类建议和下一步动作。
- [ ] 桌面端“业务分流与进度”默认可见。
- [ ] 附件展示文件类型、大小和处理状态，并可预览/下载。
- [ ] 短邮件正文不会保留大面积固定空白；原始 HTML 可按需查看。
- [ ] 不会自动访问邮件中的外部链接。
- [ ] 首次点击提取按钮在网页请求内不执行 PDF/OCR；页面应立即返回并显示后台进度。
- [ ] 提取完成后可打开已有内销模板；失败时显示原因并允许重新提取，重复点击不重复创建并行任务。
