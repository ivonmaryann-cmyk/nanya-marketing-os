# 模块 01：订单自动化修复整改清单

> 状态：第一批兼容修复已完成；PostgreSQL 切换与需业务拍板项目待执行。
> 更新日期：2026-08-24
> 范围：业务邮箱抓取、订单分流、录单模板、规则管理及订单自动化 PostgreSQL 切换。

## 审查结论

订单自动化现有流程可用，但在邮件量、规则数量和多人协作增加后，会出现同步请求阻塞、重复扫描、规则重算开销及协作隔离问题。

以下整改项中，A1、A2、A3（第一阶段）、B1、B2、B3、C1、C4（通用规则部分）、C5 已完成兼容修复并通过回归测试；C6/C7 受制于独立 PostgreSQL 测试库和正式切换窗口；B4、B5 需要先确定业务口径；D2 与当前“只保留一份兜底备份”的既定决定冲突，暂不实施。

## 已确认决策

- 通用分流规则：改为全公司共享（Global）。
- PostgreSQL：尽快完成正式切换，但必须先通过测试库、数据对账及回滚演练。
- 录单模板备份：只保留一份最近的可恢复备份，不改为多版本历史。

## 待确认决策

- 变更类型是否与通用规则一起全局共享：建议“是”。
- 全局规则编辑权限：建议仅管理员可编辑；已登录用户可查看。
- 团队协作模型：共享邮箱的可见范围、转派、交接与责任人规则。
- 同 PO 邮件的版本识别规则：不能仅按 PO 号自动合并，需定义转发、补充、修改订单的判定口径。

## 推荐实施顺序

1. **规则与数据模型收敛**：C1 + C2 + C3 + C4 + C5。
2. **PostgreSQL 验证与切换**：C6 → C7。
3. **性能与异步化**：A1 → A2 → A3。
4. **正确性与可追溯性**：B1 → B2 → B3；确定口径后处理 B4、B5。
5. **产品闭环**：D1、D3、D4。

> 不建议在 SQLite 上继续扩大异步、多进程和多人并发能力；完成 PostgreSQL 切换后再推进 A1～A3，风险更低。

## A. 上线与性能

### A1 邮件抓取任务异步化与定时抓取

- **状态**：代码完成；服务器 cron 配置待部署时执行。

- **优先级**：P0。
- **现状**：订单自动化同步路由直接调用 `fetch_latest_order_mails()`，请求线程完成 IMAP 连接、拉取、解析及落盘后才返回。
- **位置**：
  - `fangzheng_web_app/routes.py`：`order_automation_sync`、`order_automation_history_sync`
  - `fangzheng_web_app/mail_transcode_agent/mail_fetch_service.py`：`fetch_latest_order_mails`
- **已完成**：
  - 保留 `mail_fetch_tasks`，新增独立 `mail_fetch_worker.py`；同步按钮只创建 queued 任务并立即返回。
  - 页面在 queued/running 时每 5 秒刷新一次，任务完成后显示最新结果；重复点击不会为同一邮箱并发创建任务。
  - 新增 `mail_fetch_scheduler.py`，可由 cron 每日调用来为启用邮箱排队抓取。
- **注意**：现有 `job_control.launch_job_process()` 和 `job_worker.py` 面向 `jobs` 表的计算任务，不能不改造就直接套用到 `mail_fetch_tasks`。
- **验收**：点击同步立即返回；任务状态完整经历 queued/running/completed/failed；定时任务可配置且可审计。

### A2 `bootstrap_cases` 增量、幂等化

- **状态**：已完成。

- **优先级**：P0。
- **现状**：列表访问默认调用 `bootstrap_cases()`，会查询该员工邮箱下的全部邮件，并对每条执行 `INSERT OR IGNORE`。
- **位置**：`fangzheng_web_app/order_intake_service.py`：`bootstrap_cases()`、`list_cases()`、`list_date_counts()`。
- **已完成**：按“员工 + 邮箱”保存 `intake_processed_max_mail_id` 游标，只读取该邮箱的新邮件；首次运行仍完整补齐历史，之后刷新不再扫历史全表。case 的数据库唯一约束继续兜底，重复执行不会重复建档。
- **验收**：连续刷新列表不再扫描历史全表；仅新增邮件创建 case；重跑不会重复创建。

### A3 规则保存增量重算与附件惰性解析

- **状态**：核心优化已完成；超大规模批量重算任务化待 PostgreSQL 切换后实施。

- **优先级**：P0。
- **现状**：保存通用规则或变更标签后，`reclassify_cases()` 重算该员工所有非手工 case。规则含 `attachment_content` 时，首次重算会同步解析全部附件。
- **位置**：`fangzheng_web_app/order_intake_service.py`：`save_universal_rule_scope()`、`save_change_tag()`、`reclassify_cases()`、`_attachment_content()`。
- **已完成**：规则变更只重算未归档、非人工处理，且正文/主题/附件名称/附件文本命中“本次旧词或新词”的活动 case；附件文本只由后台抓取 worker 解析并缓存，规则保存和列表打开仅使用缓存，不再同步解析 PDF/Excel。
- **待续**：当活动 case 规模再增大时，将“全公司规则变更”进一步拆为可观测的批量重算任务。
- **验收**：规则保存请求不再同步跑 PDF/Excel 解析；重算 SQL 有明确的账户/时间范围；全量重算有任务进度。

## B. 正确性、健壮性与可追溯性

### B1 收敛两套邮件分流实现

- **状态**：已完成（保留旧 `classify_mail()` 作为兼容测试入口）。

- **优先级**：P1。
- **现状**：生产使用 `reclassify_cases()`；`classify_mail()` 是另一套正则逻辑，主要由测试覆盖，默认结果也不完全一致。
- **已完成**：已提取 `_rule_decision()` 纯函数供生产重算直接调用，并补充生产路径回归；旧 `classify_mail()` 不再作为生产路由依据，为不破坏原有调用暂时保留。
- **验收**：生产路径有直接测试；不存在与生产不一致的孤岛分流实现。

### B2 附件处理资源上限

- **状态**：已完成。

- **优先级**：P1。
- **现状**：PDF、Excel、Word 解析缺统一大小、页数、行数限制；Word 转换仅有 45 秒超时。
- **已完成**：邮件附件与录单提取统一限制 20 MB；邮件 PDF 限 20 页、Excel 限 20,000 行，Word 继续保留 45 秒转换超时。超限写入 `too_large` 并跳过，不阻塞页面请求。
- **验收**：异常或超大附件不会卡住请求、耗尽内存或触发无限解析。

### B3 自动分流决策历史

- **状态**：已完成。

- **优先级**：P1。
- **现状**：case 只保存最新 `routing_reason` 与 `routing_matches_json`；`order_intake_case_events` 主要记录人工调整。
- **已完成**：分流结果变化时写入 `auto_reclassify` 事件，保存 before/after、命中规则与时间；未变化 case 不重复写审计记录。
- **验收**：可追溯某封邮件在某次规则变更后的系统分流依据。

### B4 PO 去重和版本链

- **优先级**：P1，**需业务口径后实施**。
- **现状**：case 唯一性为 `(employee_id, mail_id)`；同 PO 的转发、追加、变更邮件不会形成自动链路。
- **整改**：先形成“候选关联”而非强制合并，候选依据可包括客户、PO、邮件线程、主题、时间及附件；人工确认后建立版本链。
- **验收**：同 PO 可查看关联邮件和版本链；不同业务事件不会被错误合并。

### B5 邮件归属与团队协同

- **优先级**：P1，**需产品口径后实施**。
- **现状**：case 按 `mail_accounts.owner_employee_id` 隔离，其他协作者不可见。
- **整改**：确定共享邮箱、可见范围、领取/转派/交接和审计责任后，新增 assignee/team scope 模型并调整查询权限。
- **验收**：团队成员按授权协作处理同一邮箱，所有转派和处理人变更可追溯。

## C. 全局规则与 PostgreSQL 切换

### C1 通用规则 Global 共享

- **状态**：已完成。

- **优先级**：P0，已确认。
- **现状**：`order_mail_rule_groups`、`order_change_tags`、种子键均按 `employee_id` 隔离。
- **已完成**：引入 `GLOBAL_RULE_OWNER = "__global__"`；规则读取、保存、种子和清理统一使用该 owner。保存共享规则会重算各员工的活动 case。
- **验收**：不同员工看到同一套通用规则；任一规则改动对所有业务邮箱生效。

### C2 变更类型全局化

- **优先级**：与 C1 同批，待确认。
- **建议**：全局化。否则通用分流全局、订单变更标签个人化，会产生不同员工看到不同分流结果的问题。

### C3 全局规则编辑权限

- **优先级**：与 C1 同批，待确认。
- **建议**：管理员可编辑、所有登录用户可查看；审计事件记录真实操作 employee id。

### C4 历史规则数据合并

- **状态**：通用规则部分已完成；变更类型部分等待 C2 决策。

- **优先级**：P0，随 C1/C2 实施。
- **已完成**：通用规则在首次运行时按“名称 + 动作 + 检索位置 + 关键词”幂等合并至全局 owner，并写入 metadata 迁移标记；旧个人规则保留为只读回退数据，不参与后续路由。
- **注意**：不建议仅写一次性裸 SQL；迁移需要在 SQLite 旧数据和 PostgreSQL 目标数据的切换流程中均可验证。
- **验收**：迁移后仅有一份全局规则集，无重复关键词，旧规则不丢失。

### C5 移除订单模块对 `settings` 的隐式方言依赖

- **状态**：已完成。

- **优先级**：P0，已确认尽快切 PostgreSQL。
- **现状**：PostgreSQL 方言层通过正则把所有 SQL 中的 `settings` 替换为 `automation_metadata`；订单规则种子键依赖此隐式转换。
- **已完成**：订单自动化通过显式 metadata helper 读写：SQLite 使用兼容的 `settings`，PostgreSQL 明确使用 `automation_metadata`，不再依赖正则方言替换才能正确工作。全局替换层仍为其它旧模块保留。
- **验收**：订单自动化不再查询 `settings`；跨库结果一致。

### C6 冻结方言面并补全跨库 golden 测试

- **状态**：待独立 PostgreSQL 测试库。

- **优先级**：P0。
- **现状**：已有 SQLite→PostgreSQL 翻译、20 表 copy、影子同步、切换/回滚工具；但 PostgreSQL 集成测试因未配置测试库会跳过。
- **整改**：配置独立 PostgreSQL 测试库；对 `GROUP_CONCAT`、`INSERT OR IGNORE`、`ON CONFLICT`、`RETURNING`、布尔值、日期函数及 metadata 映射做双库 golden 测试。
- **验收**：自动化相关 PostgreSQL 集成测试实际执行而非 skipped；结果与 SQLite 预期一致。

### C7 正式切换 PostgreSQL

- **状态**：待执行（不可在未指定目标库及回滚窗口时自动执行）。

- **优先级**：P0，已确认。
- **现状**：`automation_migration` 已包含 20 张自动化业务表、copy、核验、shadow、观测、cutover 和回滚演练工具。
- **整改流程**：测试库迁移 → 数据/文件核验 → 影子同步及观察 → 切换前检查 → 正式 cutover → 回滚演练。
- **验收**：20 表对账零差异；文件核验通过；至少完成一次可证明的回滚演练；应用显式启用 PostgreSQL 后业务流程可用。
