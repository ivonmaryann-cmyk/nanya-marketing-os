# 客户档案与客户规则配置（PostgreSQL）开发说明

> 文档状态：待开发
> 适用范围：订单邮件自动化（邮件分流、客户识别、内销录单提取）
> 最后更新：2026-08-21
> 关联原型：订单邮件分流、邮件详情、内销录单模板及客户档案原型
> 数据库策略：本模块以 PostgreSQL 为目标数据存储；必须沿用自动化模块现有的可回退数据访问入口。

## 1. 背景与目标

现有订单邮件分流已能按通用关键词将邮件初步分为“录单、修改订单、报价、待业务分流、暂不分流”，并支持将录单邮件提取至内销模板。实际业务中，不同客户的发件人、邮件格式、附件表头和字段含义不同；只依赖通用规则会造成两类问题：

1. 邮件无法稳定识别属于哪个客户，无法确定由哪位营管内勤负责；
2. 同一个附件字段在不同客户的订单中含义不同，无法可靠地填入内销模板。

本期新增“客户档案”这一独立菜单和客户专属规则能力，形成以下业务链路：

`邮件同步 → 通用分流 → 客户识别 → 客户专属分流/提取映射 → 业务核对与保存 → 后续151/ERP接口`

目标不是重新设计整个系统，而是在现有白色左侧导航、浅蓝背景、圆角卡片、邮件列表+右侧工作闭环的视觉与交互框架中增加可维护能力。

## 2. 范围与非范围

### 2.1 本期范围

- 客户基础档案的导入、查询、维护与停用；
- 客户与营管内勤、业务、技术支持的责任关系维护；
- 按发件人、域名及明确证据识别客户；
- 客户专属邮件分流规则；
- 客户专属的订单提取字段映射；
- 在邮件详情、内销模板中展示匹配结果、提取来源和人工待填项；
- 完整保存规则版本、匹配证据、操作事件与模板提取快照。

### 2.2 不在本期范围

- 不改变现有通用分流规则的业务含义；
- 不自动推断不确定的客户、字段或数量；
- 不接入151、410、OA或ERP写入接口；
- 不将客户编号与账款客户编号建模为一对多关系。当前将**客户编号视为客户唯一编号**；
- 不实现权限体系或数据隔离。当前所有登录用户均可查询、编辑全部客户及其规则；仅提供“我的负责客户”作为可选筛选条件；
- 不改动内销Excel原模板的行列、字段、必填定义或视觉结构。

## 3. 已有数据库迁移能力与本期约束

自动化模块已具备 PostgreSQL 数据访问与回退框架：

- 数据访问必须经 `fangzheng_web_app.database.automation_cursor()`（业务服务中现别名为 `db_cursor`）执行；
- 当 `AUTOMATION_DATABASE_BACKEND=postgresql` 且 `AUTOMATION_POSTGRESQL_READ_WRITE_ENABLED=true` 时，自动化模块读写 PostgreSQL；未开启时继续使用SQLite；
- 非自动化模块数据库和页面不得因本功能改动而切换；
- PostgreSQL结构变更只能新增版本化迁移，放入 `migrations/automation/postgresql/`，不得在运行时临时建表；
- 当前迁移报告确认本地自动化模块已可切至 PostgreSQL，但生产正式切换仍需代表性数据核对、最小权限/SSL、7天影子观察和业务验收。不得将本期开发等同于生产切换完成。

本期所有新表均属于自动化域，使用 PostgreSQL 存储。SQLite保留同结构迁移/兼容能力，作为未正式切换及回滚时的默认后端，不改变现有业务逻辑。

## 4. 全局业务流程与判断顺序

### 4.1 邮件到任务的主流程

1. 只读IMAP同步邮件与附件，创建或去重邮件记录；
2. 一封邮件创建一个独立的 `order_intake_case`（业务任务），不与其他邮件合并录单；
3. 执行通用分流规则，产生录单、修改订单、报价或未明确结果；
4. 执行客户识别。客户识别只记录明确结果，不以模糊猜测覆盖未匹配状态；
5. 若客户已明确，依次运行该客户已启用的专属分流规则、订单提取映射；
6. 若需要录单，生成/刷新该邮件唯一对应的内销录单模板；一个邮件可有多条订单明细，每条订单一行；
7. 业务人员核对、编辑模板并保存。保存的数据、下载的Excel及未来接口请求均以保存后的模板版本为准；
8. 后续151/ERP接入时，读取已保存的模板版本，不重新从邮件临时解析。

### 4.2 客户识别优先级（必须固定）

| 优先级 | 识别方法 | 自动写入客户的条件 | 处理结果 |
|---|---|---|---|
| 1 | 发件人邮箱精确匹配 | 一个启用客户唯一命中 | 自动匹配 |
| 2 | 发件人别名/已维护联系人邮箱 | 一个启用客户唯一命中 | 自动匹配 |
| 3 | 邮箱域名匹配 | 该域名只关联一个启用客户 | 自动匹配 |
| 4 | 明确的客户专属识别规则 | 同一规则集只产生一个客户 | 自动匹配 |
| 5 | 其他情况 | 无命中、多个客户命中、信息不足 | 保持“待业务确认” |

不得仅根据邮件主题中的相似客户名称、正文中的模糊简称、历史发送频率或大模型猜测自动指定客户。若不是100%明确的值，必须留空并交由业务选择。

### 4.3 分流判断顺序

1. 先执行通用分流规则；
2. 客户识别成功后，再执行该客户的专属分流规则；
3. 客户规则只能补充或明确该客户邮件，不能静默覆盖人工已经调整的分流结果；
4. 同时命中不同一级分类时，结果为“待业务分流”，并记录所有命中证据；
5. 未命中任何规则时，为“暂不分流”；
6. “修改订单”可同时附带多个变更类型（交期/发货日期、价格、数量、规格型号、订单版本/PO、取消/暂停等），但变更类型不与录单/报价/修改订单并列为一级分类。

## 5. 页面与交互设计

### 5.1 左侧导航

在现有左侧菜单中增加独立一级项 **客户档案**，位置建议为“功能中心”之后、“我的配置”之前。该菜单支持现有的收窄/展开模式：收窄时只保留图标和悬停说明，不改变内容区域结构。

不把客户档案放进“通用规则”或邮件详情页内，因为客户信息、责任人、联系人和提取规则都是长期主数据，且将被多个邮件任务复用。

### 5.2 客户档案列表页

沿用现有生产页面风格：固定左侧导航、固定页面头、列表区独立滚动。列表默认按“启用、客户名称”排序，支持关键字、责任内勤、状态筛选和分页。“我的负责客户”只是快捷筛选，不限制其他客户的查看与编辑。

建议列：

| 列 | 说明 |
|---|---|
| 客户编号 | 当前唯一编号，导入和后续规则关联主键 |
| 客户名称 | 业务展示名称 |
| 内勤负责人 | 显示内勤姓名；工号可为空 |
| 业务负责人 / 技术支持 | 以业务提供的姓名/文本维护，可为空，多人以简洁标签展示 |
| 已维护发件人 | 数量和关键邮箱/域名摘要 |
| 邮件规则 | 启用条数 |
| 提取映射 | 启用条数与模板版本 |
| 状态 | 启用/停用 |
| 操作 | 查看、编辑、停用 |

“新增客户”“导入客户”放在标题区右侧。删除只允许逻辑停用；已经关联邮件、案例或模板的客户不可物理删除。

### 5.3 客户详情/编辑页

使用顶部客户摘要卡片与页签，不采用一页堆叠所有配置。页签如下：

1. **基础信息**：客户编号、名称、额度及业务提供的基础字段；
2. **责任人与联系人**：内勤、业务、技术支持；已知发件人邮箱、域名、别名；
3. **客户邮件分流**：只维护该客户的专属分流条件和目标一级分类；
4. **订单提取映射**：只维护该客户订单文件字段如何进入当前内销模板；
5. **变更记录**：导入、修改、停用、规则调整的审计记录。

编辑操作必须显式点击“保存”，保存后创建不可修改的事件记录；不使用难以理解的自由文本规则或正则作为默认维护方式。

### 5.4 客户邮件分流规则页签

每条规则使用业务可读的“如果—那么”卡片/表格：

`如果 [邮件主题/正文/附件名称/附件内容] 包含 [关键词]，则归入 [录单/修改订单/报价]。`

一条规则可配置多个条件；条件默认“全部满足”，界面明确显示“任一满足/全部满足”。规则属性包括名称、启用状态、优先级、说明。所有已启用条件会显示检索位置，业务无需理解技术表达式。

客户规则仅对已识别为该客户的邮件生效。页面需显示“该规则不会影响其他客户邮件”。

### 5.5 客户订单提取映射页签

映射页是本期核心，必须围绕**当前内销模板**而非OCR原始字段设计。界面一行代表一个目标模板字段：

| 模板字段 | 是否业务填写 | 来源类型 | 客户文件字段/表头 | 处理方式 | 规则状态 |
|---|---|---|---|---|---|
| 客户产品编号（必填） | 自动提取；不确定留空 | 附件表格列 | 如“Material Code/物料编码” | 直接取值 | 启用 |
| 客户规格（选填） | 自动提取；不确定留空 | 附件表格列 | “Description/物料描述”+“Material Name/物料品名” | 拼接 | 启用 |
| 数量（必填） | 自动计算；不确定留空 | 数量列+单位/规格 | Quantity、Unit、规格文本 | CCL直接；PP按类型计算 | 启用 |
| 出货日期（选填） | 自动提取；不确定留空 | 附件表格列 | Required Delivery Date等 | 日期标准化 | 启用 |
| 税前单价/单价（选填） | 自动提取；不确定留空 | 附件表格列 | 不含税单价等 | 数字标准化 | 启用 |
| 产品编号、品名 | 不从客户订单抓取 | — | — | 始终留空，后续151填充 | 固定 |

映射的“来源类型”限定为：邮件主题、邮件正文、附件名称、附件文本、附件表格列、附件文件信息。对于表格列，维护者通过“文件样例预览 → 选择表头/列”选择，不手输不透明的列号。拼接、取首个明确值、日期标准化、单位换算、保留为空为有限且可说明的处理方式。

数量规则需内置以下受控策略：

- CCL：直接使用订单明细的数量；
- PP小片：数量单位为“张”，直接使用明确数量；
- PP非小片：从规格中提取明确的米数（接受 `米`、`M`、`m`）并乘以数量；提取不到或单位不明确时留空；
- PP规格中的米数可按配置写入备注；客户订单备注也可写入备注；
- 任何规则不得为了填满模板猜测单位、米数、产品编号或客户信息。

### 5.6 订单邮件分流、详情与模板页的联动

- 邮件列表：若客户已识别，在分类标签旁增加简洁“客户：xxx”标签；若未识别显示“客户待确认”，不可伪造客户名称；
- 邮件详情：固定顶部展示邮件时间、一级分类、客户识别状态、当前工作节点。返回时保留进入前的日期、分类页签、页码和滚动位置；
- 邮件详情右侧抽屉/页签：展示客户匹配证据、可人工选择客户、通用/客户规则命中情况和系统计算的处理节点；业务人员不手工填写任务状态；
- 内销模板：保持真实Excel模板结构不变。自动提取单元格以蓝点/来源提示展示，待填写项以当前黄色提示展示。刷新图标只重新提取本邮件订单内容并写入草稿模板；刷新前必须提示“将覆盖未保存的自动提取结果，不覆盖已保存的人工修改”。

## 6. PostgreSQL 数据模型

### 6.1 新增表

下列名称为实现约束，字段可因项目现有编码规范微调，但业务含义不可缺失。迁移文件建议为 `migrations/automation/postgresql/0004_customer_archive_and_rules.sql`，并同步添加SQLite兼容迁移和迁移测试。

| 表 | 核心字段 | 用途 |
|---|---|---|
| `automation_customers` | `id`、`customer_code`（唯一）、`customer_name`、`credit_amount`、`source_payload_json`、`status`、创建/更新审计字段 | 客户主档；原始导入字段保留在快照中，便于追溯 |
| `automation_customer_assignments` | `customer_id`、`assignment_role`、`assignee_name`、`employee_id`（仅内勤可空）、`effective_from/to`、`enabled` | 内勤、业务、技术支持等责任关系；当前以姓名/文本保存，内勤工号暂可为空，后续再建立用户关联 |
| `automation_customer_contacts` | `customer_id`、`contact_type`、`normalized_value`、`display_value`、`enabled` | 发件人邮箱、域名、联系人别名等客户识别依据 |
| `automation_customer_rule_sets` | `id`、`customer_id`、`rule_set_type`、`name`、`version`、`enabled` | 客户专属分流/提取规则集的版本容器 |
| `automation_customer_routing_rules` | `rule_set_id`、`name`、`action_type`、`match_mode`、`priority`、`enabled` | 客户专属邮件分流规则 |
| `automation_customer_routing_conditions` | `routing_rule_id`、`source_scope`、`operator`、`expected_value`、`sort_order` | 分流条件，来源范围仅限主题、正文、附件名、附件内容 |
| `automation_customer_extraction_mappings` | `rule_set_id`、`target_field`、`source_type`、`source_selector`、`transform_type`、`transform_config_json`、`certainty_policy`、`enabled` | 当前内销模板目标字段的取值映射 |
| `automation_customer_rule_events` | 规则/客户对象、操作、前后快照、操作者、时间 | 审计与回滚定位 |
| `order_entry_template_extraction_runs` | `template_id`、`case_id`、`customer_id`、`rule_set_version`、`trigger_type`、`status`、`created_at` | 每次首次提取/刷新提取的不可变运行记录 |
| `order_entry_template_field_sources` | `run_id`、`template_line_id`、`field_key`、`source_ref`、`source_value`、`extracted_value`、`certainty` | 支撑模板蓝点“查看来源”，保存字段级证据 |

### 6.2 既有表的最小扩展

`order_intake_cases` 增加：

- `customer_id`（可空，关联客户档案）；
- `customer_match_method`（exact_email / alias_email / unique_domain / customer_rule / manual / unmatched / ambiguous）；
- `customer_match_rule_id`（可空）；
- `customer_match_evidence_json`；
- `customer_matched_at`、`customer_matched_by`；
- `customer_snapshot_json`（匹配当时的客户编号、名称、责任人快照）。

保留既有 `customer_code`、`customer_name`，作为邮件任务的历史快照兼容字段，不用主档更新覆盖。`order_entry_templates` 与 `order_entry_template_lines`不修改真实模板字段含义；新提取运行和字段来源用新增表保存。

### 6.3 数据隔离、索引与删除策略

- 客户档案是企业主数据，不按当前登录 `employee_id` 分片；当前所有登录用户可查看和维护全部数据，“我的负责客户”仅为列表筛选；后续权限可依据 `automation_customer_assignments` 扩展可见范围；
- 邮件、案例、模板继续保持现有 `employee_id` 审计归属；
- 邮箱和域名匹配值必须规范化（去首尾空格、小写）；
- 为 `customer_code`、`customer_name`、启用状态、联系人规范值、规则集类型/状态及案例的 `customer_id` 建立索引；
- 已被邮件任务引用的客户、联系人和规则不可物理删除，只能停用；
- 外键使用明确的删除限制，避免误删客户主档导致历史订单任务无法查看。

## 7. 服务、接口与职责边界

建议新增以下服务，均通过 `automation_cursor()` 访问数据库：

| 服务 | 职责 |
|---|---|
| `customer_archive_service.py` | 客户导入、查询、编辑、停用、责任人/联系人维护 |
| `customer_identification_service.py` | 邮件客户识别、证据生成、人工确认与案例快照 |
| `customer_rule_service.py` | 客户分流规则、条件、规则版本与审计 |
| `customer_extraction_mapping_service.py` | 表头选择、字段映射、数量换算和来源证据 |
| `order_entry_service.py`（扩展） | 调用映射服务创建/刷新内销模板；保留模板版本保存逻辑 |
| `order_intake_service.py`（扩展） | 在通用分流后触发客户识别与客户规则，不改现有人工分流优先级 |

页面接口可沿用当前Flask路由风格，至少覆盖：客户列表/详情/保存/停用/导入、联系人维护、客户分流规则维护、客户提取映射维护、案例客户人工确认、模板重新提取。当前所有登录用户均可执行这些操作；所有写入记录当前操作者，操作者展示名称缺失时回退显示工号。

## 8. 客户初始数据导入方案

业务提供的 `_HB002_客户基本信息.xlsx` 作为初始来源，但不得直接写入正式表。

1. 上传后进入临时预览，展示工作表、行数、可识别列和未映射列；
2. 维护“Excel列 → 客户档案字段”映射；客户编号、客户名称至少需明确；
3. 内勤人、业务、技术支持均按业务表中的姓名/文本原样导入；内勤工号当前可为空，不做姓名到工号的自动关联，也不因缺少工号阻断导入；
4. 邮箱/域名不从客户名称猜测，不因导入表缺少邮箱而自动创建联系人；
5. 按客户编号检查重复：完全相同且业务确认后可更新，名称相似或编号冲突必须阻止正式导入；
6. 正式导入写入批次结果和每行审计，支持下载错误清单；
7. 导入完成后由业务在客户详情中补充已知邮件发件人和客户专属映射。

## 9. 数据安全、刷新与历史处理

- 客户主档与规则更新只影响后续识别/刷新，不回写已保存的模板、已人工分流的邮件或历史案例快照；
- 对历史邮件重新识别/重新分流必须是单独的批量工具，先预览差异、选择范围、确认后执行，并记录批次；
- 内销模板刷新仅针对一封邮件及其唯一模板。未保存自动提取结果可覆盖；已保存的人工修改不得静默覆盖，需明确选择“重新生成自动提取草稿”或保留当前版本；
- 下载Excel与未来接口提交均读取已保存模板版本。附件仍按现有文件存储接口读取，保持“新对象键优先、旧路径回退”，本期不搬迁或删除历史附件；
- 任何连接串、邮箱授权码、邮件正文和附件全文不得写入审计日志或异常页面。

## 11. 验收标准

1. 客户档案可由初始Excel安全导入，重复和不明确责任人可识别、可处理；
2. 已维护的唯一发件人邮箱邮件可自动识别客户；同域多客户或其他不确定情形不会自动指定客户；
3. 客户规则不会影响其他客户，人工已调整的邮件不会被后续规则覆盖；
4. 映射页面可由业务人员基于文件样例选择字段，无需编写正则或数据库语句；
5. 客户产品编号、规格、数量、日期、单价的自动值都能查看来源；不确定值为空；
6. CCL、PP非小片、PP小片三种数量策略符合已确认规则；
7. 一封邮件只对应一个录单模板，模板内可有多行订单；保存后刷新、下载和未来接口均使用同一保存版本；
8. 新模块使用 PostgreSQL 自动化数据通道，未开启Pg开关时可安全回退SQLite；非自动化现有模块回归测试通过；
9. PostgreSQL迁移、导入、规则修改、手工确认均具备审计记录；
10. 不得产生自动猜测填值、物理删除历史引用客户或无确认批量重跑行为。

## 12. 风险与注意事项

| 风险 | 控制措施 |
|---|---|
| 客户邮件没有客户编号 | 依赖已维护发件人/唯一域名/明确规则；不明确即待确认 |
| 同一域名服务多个客户 | 禁止域名自动匹配，要求精确邮箱或人工确认 |
| 客户附件格式变化 | 映射规则按版本保存；刷新保留证据并提示待维护映射 |
| OCR/表格解析误读 | 仅写入明确结果；字段级来源可回看；其余留空 |
| 主档变更污染历史任务 | 案例、模板保存客户/规则快照，不回写历史 |
| Pg生产切换风险 | 遵循现有迁移计划，完成代表数据、权限SSL、影子运行及业务验收后再正式启用 |
| 登录只有工号 | 审计先按工号；用户档案接入后补充姓名展示，不阻塞本期功能 |
