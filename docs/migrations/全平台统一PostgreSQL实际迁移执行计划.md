# 全平台统一 PostgreSQL 实际迁移执行计划

> 文档性质：开发环境全平台数据库迁移的唯一执行台账。
> 目标库：`nanya-automation-dev`（单一 PostgreSQL 开发库）。
> 当前状态：进行中。
> 最后更新：2026-08-27。

## 1. 目标与边界

将南亚营销自动化平台的全部业务数据迁入一个 PostgreSQL 开发库，并让应用所有模块统一从该库读写。

本次范围：

- 用户、登录、账号状态与权限数据；
- 全局设置、规则与 AI 配置；
- 邮箱账号、邮件、附件索引、抓取任务、分流规则；
- 客户档案、联系人、客户规则、客户规格匹配；
- 订单案例、录单模板、明细、版本、料号任务、接口配置与交互审计；
- PP/通用转码、价格计算、共享后台任务；
- 工作规划、个人任务与反馈；
- 迁移需要的表结构、索引、序列和审计元数据。

本次不包含：

- 生产环境切换；
- 邮件、附件、Excel、PDF、任务输入输出文件的物理搬迁；
- 删除 SQLite、旧本机 PostgreSQL 或现有文件；
- 云对象存储改造。

文件本体保持现有路径；仅迁移数据库中的文件索引、路径、大小和哈希信息。

## 2. 统一架构

```text
南亚营销自动化平台（全部模块）
              │
              ▼
  nanya-automation-dev（一个 PostgreSQL 开发库）
              │
              ▼
  用户 / 配置 / 转码 / 任务 / 邮件 / 客户 / 订单 / 工作规划等全部业务表
```

最终只维护一套本地数据库配置：

```env
PLATFORM_DATABASE_BACKEND=postgresql
PLATFORM_DATABASE_URL=postgresql://<用户>:<密码>@<主机>:<端口>/<数据库>
PLATFORM_DATABASE_READ_WRITE_ENABLED=true
```

现有分模块数据库环境变量仅保留为旧配置兼容；迁移完成后，日常开发不再要求逐模块填写连接信息。账号密码只保存于 `config/local.env`，不得提交到 Git 或写入本文件。

## 3. 执行原则

1. 每张业务表必须有唯一权威来源；不得将 SQLite 与旧本机 PostgreSQL 的同类数据混合拼接。
2. 先备份、审计、迁移、核对，再切换；任一核对失败不得切换。
3. 迁移期间停止应用和后台 Worker 写入，保证迁移时间点一致。
4. 迁移采用幂等写入和事务；失败时目标数据库回滚。
5. SQLite、旧 PostgreSQL 和历史文件至少保留 30 天，只读保存，不删除。
6. 每完成一个步骤，必须更新本文件中的状态、执行时间、执行人、报告路径和结果。

### P1：全平台权威来源盘点

**状态：已完成**

执行内容：

1. 盘点 `storage/app.db` 的全部表、行数、更新时间、完整性；
2. 盘点旧本机 PostgreSQL 的全部表、行数、更新时间；
3. 按业务域确定唯一权威来源；若同一域两边都有数据，以最新且完整的一边为准，不自动合并；
4. 生成全平台表清单，并标记：迁移、仅建表、无需迁移、待补迁移脚本；
5. 重点复核近期新增的订单接口维护、料号查询、订单明细事件和邮件回复草稿等表是否纳入。

**产出：** `docs/migrations/全平台迁移来源盘点报告-YYYYMMDD.md`；后续执行脚本再生成 `outputs/migrations/platform-source-inventory-YYYYMMDD.json`。

**完成条件：** 每张目标表都有唯一来源、预计行数和负责人确认。

**回退：** 只读盘点，无需回退。

**逐表映射清单：** `docs/migrations/全平台迁移逐表映射清单-20260827.md`。

#### P1.1 已确认的来源边界（2026-08-26）

| 业务域 | 唯一权威来源 | 盘点依据 | 迁移处理原则 |
|---|---|---|---|
| 邮件、客户、订单自动化、接口维护与料号任务 | 本机 Docker PostgreSQL（`nanya_automation`） | 40 张自动化表；客户 1,086 条、邮件 866 条、订单案例 866 条，且包含订单明细事件、接口配置、接口调用、料号任务等近期功能数据 | 仅从本机 PostgreSQL 复制这些业务表；不得再从 SQLite 追加同类记录 |
| 用户、系统设置、PP/通用转码、个人任务、反馈及非自动化平台数据 | `storage/app.db`（SQLite） | SQLite 完整性检查通过，含 60 张表；包含 `users`、`settings`、`jobs`、转码规则与任务等本机 PostgreSQL 未承载的数据 | 从 SQLite 迁移这些非自动化表；P4 需补齐对应 PostgreSQL Schema 与数据迁移脚本 |
| 迁移工具与影子比对表 | 按 P4 重新评估，不视为业务源数据 | 如 `automation_migration_outbox`、`automation_shadow_differences` 是历史迁移过程数据 | 默认不作为业务数据复制，保留来源只读归档；是否建表由 P4 决定 |

> 说明：这里的“唯一来源”按业务域划分，而非将两个来源的同类订单自动化数据合并。这样可避免同一邮件、客户、订单或审计记录重复、冲突或关联断裂。

### P2：统一数据库配置改造

**状态：已完成**

执行内容：

1. 在应用数据库配置层新增统一的 `PLATFORM_DATABASE_*` 读取入口；
2. 自动化、身份、转码、配置、工作规划模块默认复用该入口；
3. 保留原模块级环境变量的向后兼容，但不再要求日常填写；
4. 补充单元测试：统一配置启用后，五个模块均指向同一 PostgreSQL；关闭时可整体回到 SQLite；
5. 不在代码、日志、测试报告中输出密码或完整连接串。

**完成条件：** 本地仅填写一套配置即可启动应用；五个模块均能解析到同一数据库连接。

**回退：** 删除/停用统一配置，恢复 SQLite 后端；不改动业务数据。

### P3：迁移前冻结、备份与审计

**状态：已完成**

执行内容：

1. 停止 Flask、邮件同步、订单提取 Worker、转码 Worker 与其他后台写入任务；
2. 对权威来源创建一致性快照或数据库备份；
3. 计算备份 SHA256，记录备份路径、创建时间和操作者；
4. 对来源库运行完整性检查；
5. 检查邮件原文、附件、任务文件、Excel/PDF 路径、文件大小和哈希；
6. 记录各表迁移前行数、主键范围和敏感字段数量。

**产出：**

- `outputs/migrations/platform-precheck-YYYYMMDD.json`
- `outputs/migrations/platform-source-audit-YYYYMMDD.json`
- 备份文件与 SHA256 清单（仅本地保存，不提交 Git）

**完成条件：** 来源库完整性正常；文件异常清单为 0 或已书面确认；备份可读取。

**回退：** 恢复应用即可继续使用旧来源；目标库仍为空。

### P4：全平台 Schema 与迁移脚本补齐

**状态：已完成**

执行内容：

1. 根据 P1 表清单复核现有 PostgreSQL 迁移脚本是否覆盖全部平台表；
2. 为缺失表补充版本化 DDL、索引、约束、序列与数据复制逻辑；
3. 迁移顺序按依赖关系编排：用户与配置 → 共享任务/转码 → 工作规划 → 邮件/客户/订单自动化；
4. 保留原主键，迁移结束后校准各序列；
5. 所有复制均使用幂等 Upsert；同一迁移重复执行不得生成重复数据；
6. 对密码哈希、授权码密文、AI 配置密文保持原值，不解密、不重算。

**完成条件：** 空目标库可一次性建立全部平台表；迁移脚本静态测试和真实 PostgreSQL 集成测试通过。

**回退：** 目标库仍为开发空库时，仅允许在确认后清理迁移对象；绝不清理来源库。

### P5：全量迁移执行

**状态：已完成**

执行内容：

1. 再次确认 P3 备份与来源行数未变化；
2. 在 `nanya-automation-dev` 执行全部 Schema 迁移；
3. 在单事务中按既定顺序复制全部平台数据；
4. 完成后校准序列、写入迁移版本和报告；
5. 任一关键表复制或核对失败，回滚本次 PostgreSQL 事务并停止后续步骤。

**产出：** `outputs/migrations/platform-migration-YYYYMMDD.json`。

**完成条件：** 全量复制成功，目标库表、索引、序列和迁移版本完整。

**回退：** 不启用应用切换；来源库继续可用。目标库保留现场供排查，未经确认不得删除。
