## 1. 盘点范围与结论

| 数据源 | 盘点结果 | 是否作为迁移权威来源 |
|---|---|---|
| `storage/app.db` SQLite | 文件大小 33,382,400 bytes；完整性检查结果 `ok`；60 张业务/配置/转码相关表 | 是，仅用于非订单自动化平台域 |
| 本机 Docker PostgreSQL `nanya_automation` | 40 张订单自动化相关表；容器处于健康运行状态 | 是，仅用于邮件、客户、订单与接口自动化域 |

**正式迁移的来源原则：** 不将 SQLite 与本机 PostgreSQL 中同类的订单自动化记录进行拼接。订单自动化业务统一只从本机 PostgreSQL 迁移；其他尚未进入本机 PostgreSQL 的平台模块，统一从 SQLite 迁移。

### 采用本机 PostgreSQL 的依据

- SQLite 的 `automation_customers` 为 0 行，而本机 PostgreSQL 为 1,086 行；
- SQLite 的 `mail_messages` 为 824 行，而本机 PostgreSQL 为 866 行；
- SQLite 的 `order_intake_cases` 为 824 行，而本机 PostgreSQL 为 866 行；
- 本机 PostgreSQL 已有订单明细事件、接口配置、接口调用日志、料号建议与料号处理任务；SQLite 中这些表多为空或记录较旧。

因此，订单自动化数据以本机 PostgreSQL 作为唯一权威来源，SQLite 中同名自动化表不得再参与正式数据复制。

## 3. 非订单自动化域：SQLite 为唯一来源

SQLite 中存在、而本机 PostgreSQL 当前未承载的主要平台数据包括：

- 转码智能体与规则中心：`transcode_agent_confirmation_events`（13）、`transcode_agent_confirmation_items`（37）、`transcode_agent_pending_rules`（4）、`transcode_agent_row_verifications`（49）、`transcode_model_configs`（1）及 `transcode_rule_center_*` 规则表；

这些表需要在 P4 先补齐 PostgreSQL DDL 与约束，再在 P5 从 SQLite 迁移。不得因本机 PostgreSQL 尚无此类表而遗漏。

## 4. 本次不作为业务数据复制的对象

- `automation_migration_outbox`（SQLite 827 行）与 `automation_shadow_differences` 等历史迁移/影子比对数据；
- 来源库中的测试/迁移运行状态表。

它们将在 P4 逐项确认是否仅建表、重新初始化或归档保留；未经确认不得作为生产业务记录写入目标库。

## 5. P1.2：现有 PostgreSQL Schema 覆盖审计

仓库现有 `migrations/` 共识别出 72 张 PostgreSQL DDL 表定义；SQLite 的 60 张表中，58 张已有对应 DDL。

| 分类 | 结果 | P4 处理 |
|---|---|---|
| SQLite 业务/配置/转码表 | 60 张 | 逐表确认来源、主键、依赖和迁移顺序 |
| 已有 PostgreSQL DDL 对应表 | 58 张 | 复用并针对目标开发库执行版本化迁移 |
| SQLite 未对应 PostgreSQL DDL | `automation_migration_outbox`、`automation_shadow_differences` | 两者为历史影子迁移工具表，不作为业务数据复制；P4 确认是否仅建工具表或不迁移 |
| PostgreSQL DDL 额外定义 | 14 张 | 包含各模块 change log、runtime flag、schema migration、inbox/shadow 等审计和运行支撑表；P4 确认初始化规则与保留策略 |

现有迁移脚本已覆盖五类平台模块：自动化、身份、配置、转码、工作规划。缺口不在于“有没有表”，而在于尚未实现全平台单一连接配置、尚未完成一次性跨来源的数据复制与逐表对账。

逐表来源、来源行数、主键、迁移批次和初始化处置详见：[全平台迁移逐表映射清单（2026-08-27）](全平台迁移逐表映射清单-20260827.md)。
