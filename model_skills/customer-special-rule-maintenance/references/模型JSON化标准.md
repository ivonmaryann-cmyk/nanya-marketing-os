# 模型JSON化标准

## 输入边界

- 一次只处理一条候选规则，必须携带候选ID、客户代码、客户简称、来源行、业务字段和原文。
- 模型输入的 `source_fields` 只保留业务原文，不把程序推断结果伪装成原文。
- 任务类型固定为 `rule_structure`，材料范围固定为 CCL。

## 输出要求

- 输出必须符合 `marketing-transcode-semantics/references/semantic-normalizer.schema.json`。
- 不得输出完整制造码或候选制造码。
- 原文写出的 AC、AM、AP、A1 等只进入 `stated_target_value`。
- 每个语义项必须保留连续原文证据。
- 多值无选择条件、输入字段不明确或规则残缺时，不得猜测，进入 `ambiguities`。

## 程序校验

程序在模型 Schema 校验后继续执行：

1. 候选ID、客户和来源行绑定。
2. 业务字段与目标字段一致性。
3. 当前八类CCL字段范围校验。
4. 条件字段、操作符和值完整性。
5. 基板级别原文目标值与有效代码表校验。
6. 原文证据连续性和原文目标值存在性。
7. 歧义、低置信和规则残缺分类。
8. `semantic_items` 必须逐项生成正式规则，不得把多项的条件和目标合并到同一行。
9. 正式原子规则必须只有一个语义类型、一个目标字段和一个非空标准值；互斥条件、重复条件和多个不同 `equals` 必须拦截。

## 状态标准

- `程序校验通过`：结构、证据、字段和值均通过，无模型歧义。
- `待业务确认`：结构通过，但存在多值、缺字段、低置信或业务选择条件不清。
- `程序校验失败`：JSON、证据、字段或值校验失败，不能进入审核通过状态。

## 执行方式建议

- `结构化后可确定性执行`：固定关键词、缺失判断、排除集合、字符位置、比较、外部查表等可由程序执行。
- `运行时需要模型`：订单原文仍需开放式语义归一，不能通过固定条件稳定判断。
- `待业务确认`：必须先补充业务口径。
- `无法解析`：模型调用或程序校验失败。

任何 `程序校验通过` 都不等于业务已确认。业务确认后才能生成正式模型语义规则表。
