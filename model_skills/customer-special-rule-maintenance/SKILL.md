# 客户特殊规则维护

严格区分业务原表、结构化草稿、模型语义候选和正式执行规则。不得让业务原表或模型候选直接进入生产转码。

## 执行流程

1. 保存业务原表新版本，不覆盖上一版本。
2. 以客户代码为主键，对比新增、修改、删除的客户行。
3. 同时读取 `CCL特殊规则`、`通用特殊规则` 和 `非影响转码备注`；按内容判断是否属于CCL，不再按列名整体排除。保留业务反馈为最高可信依据。
4. 按八个当前字段拆分原子规则：胶系、基板厚度、铜箔规格、基板尺寸、胶水类别、铜箔类型及印字/非印字、基板级别、总/芯厚。
   三类来源列均使用同一八字段边界；PP、组合结构、厂商、配方、包装、标签、交期等内容仍排除。
5. 按 `references/规则分流标准.md` 标记执行路径。
6. 使用 `scripts/classify_customer_rules.py` 生成确定性分流结果和模型语义候选JSON。
7. 将客户级摘要写回草稿分流列，将一条规则一行的候选写入“模型语义规则候选”Sheet。
8. 对候选调用运行时语义Skill前，先确认所需订单字段是否真实存在。
9. 使用 `scripts/compile_semantic_rules.py` 对候选逐条离线JSON化；支持并发、重试、断点续跑和审计摘要。
10. 模型返回结果必须通过JSON结构、原文证据、目标字段、客户绑定和冲突校验，标准见 `references/模型JSON化标准.md`。
11. 业务确认后，先使用 `scripts/finalize_semantic_rule_rows.py` 将模型审计JSON拆成“一个语义项一行”，再生成标准机器规则、正式语义规则和辅助映射。
12. 使用 `scripts/publish_semantic_rules.py` 发布独立语义规则版本；发布前必须校验单一语义类型、单一目标字段、单一标准值、条件不重复/不互斥、确认状态、哈希和待确认隔离。
13. 生成受影响客户回归样本，先影子运行，再允许正式启用。
14. 更新流程文档、开发记录、提交范围、状态清单和规则版本说明。

## 资产边界

- 业务原表：业务原始表达，只追溯，不执行。
- 结构化草稿：一客户一行，用于业务确认和分流。
- 模型语义规则候选：一条规则一行，尚未批准，不执行。
- 标准机器规则：确定性规则，校验通过后执行。
- 正式语义规则：业务已确认，运行时用于匹配模型标准语义。
- 每条候选和正式规则必须保留来源列；同义规则去重后只执行一次，其他来源保留为证据。
- 辅助映射：尺寸、厚度、物料编码和外部表等确定性映射。

## 发布限制

- 不得处理PP、PP小片和RC。
- 不得让组合结构、铜箔厂商、玻布厂商和配方代码进入当前22码。
- 不得把“待模型JSON化”候选直接设为启用。
- 不得用模型解决缺少业务选择条件的多值冲突。
- 不得将同一候选中的多个语义项合并成一条AND规则。
- 不得发布标准语义值为空、含互斥条件或含重复条件的规则。
- 不得在没有回归样本和业务确认时发布新客户语义规则。

详细字段和发布步骤见 `references/维护SOP.md`。
